# Соглашение о разработке

Этот файл описывает, как в проекте называются ветки и задачи. Цель — чтобы
любой из команды, открыв репозиторий или доску, сразу
понимал, к какой задаче относится ветка и какой части проекта касается
задача — не открывая переписку и не спрашивая у автора.

## 1. Как называть ветки

Формат:

```
тип/номер-задачи-краткое-описание
```

- **тип** — одно из трёх: `feature`, `fix` или `docs` (что это значит — ниже).
- **номер-задачи** — номер issue из GitHub Projects, например `#6` → пишем
  просто `6` (без решётки).
- **краткое-описание** — 2–4 слова латиницей через дефис, о чём ветка.

Три типа веток:

| Тип | Когда использовать | Пример |
|---|---|---|
| `feature/` | Делаем что-то новое — новую функцию, новый экран, новую логику | `feature/6-struktura-dannyh-reisa` |
| `fix/` | Исправляем то, что уже было сделано и сломалось или работает неправильно | `fix/12-oshibka-rascheta-netto` |
| `docs/` | Меняем документацию, ADR, README, вики — без изменения кода | `docs/adr-001-delivery-model` |


## 2. Как называть задачи (issues) на доске

Формат:

```
[Компонент] Что сделать, одним предложением
```

- **[Компонент]** — квадратные скобки обязательны, внутри одно из трёх слов
  (список компонентов — в разделе 3).
- Дальше — глагол в повелительном наклонении (Добавить, Собрать, Написать,
  Провести — а не «Добавление» или «Нужно добавить»).

Примеры хороших названий:
- `[Весы] Добавить поле «дата рейса» в форму ввода`
- `[Интерфейс] Сделать wireframe формы ввода для весовщика`
- `[Документация] Провести интервью с весовщиком`

Примеры плохих названий (так не надо):
- `Весы` — непонятно, что конкретно сделать
- `Доработка формы` — нет компонента, нет конкретики
- `[Весы][Срочно] надо бы поправить форму` — лишние пометки, не по формату

## 3. Компоненты проекта

Всего три, они же зоны ответственности в команде:

- **Весы** — логика расчёта веса, структура данных, хранение — отвечает Тогжан
- **Интерфейс** — форма ввода, экраны, пользовательский опыт — отвечает Дана
- **Документация** — интервью, ADR, риск-лог, тестирование — отвечает Айдана

Если задача касается сразу двух компонентов — указывай тот, с которого
начинается работа, и по ходу можно завести вторую задачу для второго
компонента (так, как разбили задачу про офлайн-режим на `[Интерфейс]` и
`[Весы]` отдельно).

## 4. Как это применяется на практике

1. Взял задачу с доски (например `#6`) → перевёл в статус «В работе».
2. Создал ветку по формату из раздела 1: `feature/6-struktura-dannyh-reisa`.
3. Работаешь и коммитишь в эту ветку.
4. Когда готово — открываешь Pull Request в `main`, а не коммитишь напрямую.
5. После проверки (или самостоятельно, если ревьюера нет) — мержишь PR.

Коммит напрямую в `main`, минуя ветку и PR, — не делаем никогда, даже для
мелких правок.
