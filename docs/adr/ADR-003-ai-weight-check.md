# ADR-003: Включаем ли ИИ-функцию «Проверка веса»

**Статус:** Принято, реализовано в #61 (`app/static/weightcheck.js`)
**Дата:** 25.11.2026
**Автор:** Мырзабекова Тогжан
**Пересмотр:** после первых 2 недель сезона 2027 по реальным исправлениям в `trip_revisions`

## Контекст

- Весовщик вводит брутто вручную с табло. Форма ловит только грубые ошибки (0, больше 100 т, тара ≥ брутто).
  Правдоподобные ошибки (переставленные цифры, нетто вместо брутто) попадают в итог дня.
- Замер на 40 рейсах (`evals/README.md`): проверка по сегодняшним рейсам машины без ИИ – F1 0,71,
  ложных тревог на обычных рейсах 0 из 18. Локальная модель qwen2.5:7b – F1 0,57–0,62, ложных тревог 46–100 %,
  9–17 с на рейс, ответы меняются между прогонами.
- Приложение должно работать без связи (ADR-002), на весовой интернет нестабильный.

## Рассмотренные варианты

1. Не делать: оставить только проверку формы.
2. Правила по медиане машины за сезон (без ИИ).
3. Отклонение от сегодняшних рейсов машины (без ИИ), в браузере.
4. Внешний API (облачная LLM).
5. Открытая модель на своём сервере.

## Решение

Вариант 3. LLM не включаем. Предупреждение «Проверьте брутто» показываем, если нетто отличается от медианы
сегодняшних рейсов этой машины больше чем на 15 %; если рейсов сегодня ещё не было – правило варианта 2.
Сохранение не блокируется, подтверждение «Вес верный» записывается вместе с рейсом.

- Почему не 4: даже по тарифу gpt-6.1-sol (2 $ / 10 $ за 1 млн токенов, прайс OpenAI на 25.11.2026) это около 520 ₸ в месяц,
  но модель того же класса на замере хуже правил, нужна связь в момент взвешивания, а веса урожая хозяйства уходят
  внешнему провайдеру.
- Почему не 5: на бесплатной VM Oracle (1 ГБ ОЗУ) модель 7B не помещается, на 4 CPU раннера – 9–17 с на рейс,
  GPU-сервер от ~107 000 ₸ в месяц. И качество то же, что в варианте 4.
- Почему не 2 отдельно: recall 0,38 – пропускает почти все «нетто вместо брутто». Остаётся запасным правилом для первого рейса дня.

## Последствия

- Плюс: работает без связи, < 1 мс, 0 ₸, данные не покидают телефон и сервер хозяйства.
- Минус: ошибки меньше обычного разброса (до ~12 %) не ловит – для них нужен другой контроль (фото табло, задача на v2).
- Минус: порог 15 % подобран на синтетических данных, после сезона его надо проверить на реальных.

## Критерий пересмотра

- Через 2 недели сезона: если весовщик нажимает «Вес верный» больше чем на 10 % обычных рейсов – порог меняем.
- Если доля рейсов, исправленных после сохранения, не снизилась – функцию пересматриваем.
- LLM возвращаемся рассматривать, если появится модель, которая на этом же наборе (`evals/`) даёт F1 выше варианта 3
  и не меньше 0,8 при ложных тревогах на обычных рейсах ≤ 10 %.
