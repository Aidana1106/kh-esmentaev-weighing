# Стратегия тестирования

Проект: учёт веса зерна на весовой КХ «Есментаев». Версия от 17.11.2026 (ЛЗ 11).
Все инструменты открытые и бесплатные.

## 1. Принцип

Качество создаём решениями до разработки (критерии приёмки, DoR, DoD, ревью), а тестами измеряем.
Проверки встроены в процесс через quality gates:

| Gate | Условие прохода |
|---|---|
| Вход в разработку | Задача соответствует DoR, критерии приёмки и негативный сценарий записаны |
| Выход из разработки (PR) | CI зелёный: ruff, pytest с покрытием ≥ 60 %, gitleaks, docker build; ревью второго участника (правило «Защита main») |
| Перед релизом | Сквозной сценарий `e2e_smoke.py` и API-коллекция Bruno зелёные на стенде; свежая резервная копия; план отката (`docs/release.md`) |
| Перед приёмкой | Сценарии UAT согласованы, стенд с тестовыми данными готов (`docs/testing/uat.md`) |

## 2. Уровни и объём автоматизации

| Уровень | Чем | Что проверяет | Сейчас | Скорость | Где запускается |
|---|---|---|---|---|---|
| Модульные | pytest | Чистая логика: расчёт нетто, границы дня по часовому поясу | 0 отдельных – логика проверяется через API-тесты; план: 10+ тестов на `timeutil` и проверку весов | мс | CI |
| Интеграционные + API | pytest + TestClient + PostgreSQL 16 | Эндпоинты с настоящей базой: вход, роли, рейсы, офлайн-повтор, итоги, журнал исправлений | 25 тестов, покрытие кода 85 % | ~40 с | CI на каждый PR |
| API-контракт | Bruno (`tests/api/kh-weighing`) | Коды ответов, JSON, негативные случаи на работающем стенде | 6 запросов, 8 проверок | ~1 с | Перед релизом |
| Сквозные (E2E) | Playwright (`scripts/e2e_smoke.py`) | 13 шагов пользователя на экране телефона, офлайн, RU/KZ, клавиатура | 1 сценарий, 13 проверок | ~40 с | Перед релизом |
| Нагрузочные | Locust (`tests/load/locustfile.py`) | НФТ-01, НФТ-03, точка деградации | 3 профиля | 3 мин | Перед приёмкой и после изменений БД |
| Ручные | Чек-листы | Контраст, казахские тексты носителем языка, печать итогов, UAT | По релизу | часы | Перед приёмкой |

Пирамида у нас пока «толстая в середине»: много API-тестов с базой и мало чистых модульных. Это осознанно для MVP
(почти вся логика – SQL и проверки на сервере), но расчёт границ дня и проверки весов выносим в модульные тесты
(действие по INC-1, задача #52). Нестабильные тесты не отключаем: чиним или удаляем.

Метрики для PM: время полного прогона CI (сейчас < 1 мин) и доля зелёных прогонов main (см. `docs/dora.md`).

## 3. Тестовые данные и обезличивание

| Где | Какие данные | Как получены |
|---|---|---|
| CI и локально | Справочники хозяйства (4 машины МТЗ, 10 полей) + рейсы, которые создают сами тесты | Миграция `002_seed.sql`, база пересоздаётся на каждый прогон |
| Нагрузка | 5 000 и 15 000 синтетических рейсов за сезон 01.08–31.10, вымышленные операторы `load_op1…` | `scripts/make_test_data.py` (случайные веса и время, без реальных людей) |
| Стенд для UAT | Справочники + учётные записи `uat_operator`, `uat_admin`; рейсы вводят сами участники UAT | `app.cli create-user` (при желании заранее `make_test_data.py --trips 300`) |
| Если понадобится копия боевой базы | Пока не нужна: боевой базы ещё нет | На будущее – `scripts/anonymize.sql` |

Персональные данные в системе – это пользователи (имя, логин, пароль). При копировании боевой базы на стенд
`anonymize.sql` **заменяет** значения, а не просто удаляет фамилии: имена → «Весовщик 3», логины → `user3`,
пароль у всех – тестовый пароль стенда, сессии удаляются. Веса получают шум ±3 %, чтобы урожай хозяйства
нельзя было восстановить по итогам. Машины и поля – справочники хозяйства, не персональные данные.
Боевой базы пока нет, поэтому скрипт проверен на копии тестовой базы с 16 365 случайными рейсами: после обезличивания число рейсов то же, нетто > 0 у всех.

## 4. Среды

| Среда | Что это | Для чего |
|---|---|---|
| Локальная | `docker compose up` на ноутбуке разработчика | Разработка, ручная проверка |
| CI | GitHub Actions, PostgreSQL 16 как service | Автотесты на каждый PR и main |
| Демо-стенд | Ноутбук команды + HTTPS-туннель cloudflared (задача #37), далее VPS | E2E, Bruno, UAT, показ заказчику |
| Мониторинг стенда | Uptime Kuma в Docker (`deploy/docker-compose.monitoring.yml`), проверка `/api/health` каждые 60 с | НФТ-02, оповещение команды |

Нагрузочный тест на ноутбуке даёт только **относительное** сравнение: стенд отличается от будущего сервера.

| НФТ-07 REST/JSON, понятные ошибки | Bruno | 8/8 проверок ✅ |

Побочная находка нагрузочного теста – дефект #50: примерно 1 % запросов сразу после входа получает 401.
Обе находки заведены в трекер с severity и приоритетом.

## 6. Дефекты: severity и priority

Severity ставит тот, кто нашёл (насколько сломано технически), приоритет – Айдана как PM (насколько срочно для бизнеса).
Приоритеты и сроки – из SLA (ЛЗ 8): P1 реакция 15 мин, P2 – 2 часа и исправление за 2 рабочих дня,
P3 – ближайший релиз, P4 – без обязательств. Метки P1–P4 есть в трекере. Триаж – на дейли в среду.
Главная метрика – дефекты, найденные уже в продакшене (escaped defects).
