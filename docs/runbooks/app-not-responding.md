# Runbook: приложение не отвечает

Для кого: дежурный, который видит систему впервые. Время выполнения: ~5 минут.
Связанные материалы: дефект #51, `docs/release.md` (откат), `scripts/backup.sh`.

## Когда применять

- Uptime Kuma прислал «DOWN» по `/api/health`, или
- весовщик пишет: «не открывается», «крутится и не сохраняет», «ошибка 500».

Рейсы, введённые весовщиком в это время, **не теряются**: телефон держит их в офлайн-очереди
и отправит, когда сервер оживёт. Поэтому не торопимся с удалением чего-либо.

## 0. Сообщить

Написать в чат команды: «Весовая не отвечает, разбираюсь, следующий статус через 30 минут».
Заказчику пока не пишем – это делает Айдана, если восстановление дольше 30 минут.

## 1. Проверить, что приложение действительно не отвечает

На сервере, в папке `kh-weighing`:

```
curl -s -m 10 -o /dev/null -w "%{http_code} %{time_total}s\n" http://127.0.0.1:8000/api/health
```

| Вывод | Что значит | Дальше |
|---|---|---|
| `200 0.01s` | Приложение живо, проблема в сети/HTTPS/туннеле | Шаг 5 |
| `000 10.0s` или `500` | Приложение зависло или не может достать соединение с базой | Шаг 2 |

## 2. Посмотреть состояние контейнеров и логи

```
docker compose ps
docker compose logs --tail=50 app
```

Ожидаемое: `db` в состоянии `healthy`.
Если в логах `app` много строк `PoolTimeout: couldn't get a connection after 30.00 sec` –
это известная ситуация из дефекта #51 (пул соединений исчерпан, сам приложение не восстанавливается).

Если `db` **не** healthy – перейти к шагу 4.

## 3. Перезапустить приложение (база остаётся работать)

```
docker compose restart app
```

Подождать 10 секунд и повторить проверку из шага 1. Ожидаемое: `200`.
На учебном прогоне 17.11.2026 после перезапуска процесса приложение ответило через **2,4 с**.

Проверить с телефона: войти, открыть «Историю» за сегодня – рейсы из офлайн-очереди должны появиться.

## 4. Если не помогло: база

```
docker compose restart db
docker compose ps          # ждать db = healthy, 10–30 с
docker compose restart app
```

Снова шаг 1. Если `db` не поднимается (в логах `db` ошибки диска/данных) – **не удалять том**, перейти
к восстановлению из копии по `docs/release.md`, чек-лист отката, пункт 4. Решение принимает Тоғжан
(ответственный за релиз), без согласования.

## 5. Если приложение живо, а снаружи не открывается

```
docker compose logs --tail=30 caddy      # HTTPS-профиль
# или для туннеля: перезапустить cloudflared на ноутбуке стенда
```

Проверить срок сертификата и что домен указывает на сервер.

## 6. Как понять, что помогло

- `/api/health` отвечает `200` три раза подряд за минуту;
- Uptime Kuma показывает «UP»;
- весовщик подтвердил, что рейс сохраняется.

## 7. Если ничего не помогло за 30 минут

Позвонить Тоғжан (ответственный за релиз), Айдана сообщает заказчику: «Сервер недоступен, рейсы сохраняются
в телефоне, ведите параллельно тетрадь до восстановления».

## После

Записать случай в `docs/incidents.md` (время обнаружения, время восстановления, что помогло) – из этого журнала
считается время восстановления в метриках DORA.
